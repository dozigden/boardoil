# Forms Engine Guidance

Read this before changing the shared forms engine or migrating a form to it. See [Frontend.md](Frontend.md) for frontend and backend-validation policy, [frontend-pinia.md](frontend-pinia.md) for store ownership and feedback, and [Testing.md](Testing.md) for validation commands.

## Scope

- The forms engine is the established approach for suitable BoardOil forms. Prefer it for new ordinary CRUD forms. Existing forms migrate in explicitly agreed, reviewable slices; specialist editors can retain bespoke UI and reuse shared controls or feedback where useful.
- Card-type, slick, tag and column dialogs, inline column creation, board details/deletion, user/client-account creation and editing, administrator/self-service password reset, shared personal/client token creation, the Configuration and System Info Message pages, card transfer, bulk card editing and board creation use the shared forms engine (`shared/forms`). Their stores or existing page callbacks return the full API `Result` and own API requests/entity updates; `useForm` owns submission validation publication. Other forms keep their existing feedback paths until explicitly migrated.

## Definitions and Drafts

- Each mounted form shell uses one definition for the entire editing session, including presentation and callbacks. Create it once after loading initial data; mount a new shell for a different session. Use callbacks for live choices and permissions, and `savedValues` for adopting successful responses rather than replacing the definition.
- Field definitions use common settings plus named control types. TypeScript checks draft field names, control settings and callback drafts; form authors are responsible for matching controls and choice values to the named draft property. Keep this contract simple rather than reintroducing mapped/conditional value matching.
- Form definitions supply initial values, fields, local validation and a Result-returning submit callback. Local errors need only `message` and `validationErrors`; do not invent API metadata. `useForm` owns draft snapshots, dirty/reset state, duplicate-submission protection, retry clearing and result publication. Drafts are plain structured-cloneable data, with top-level `File | null` fields retaining immutable file identity across snapshots; custom controls replace values through `update:modelValue` rather than mutating nested props.

## Rendering and Feedback

- `FormDialog` mounts once per editing session and handles cancellation, success and explicit post-submit error focus. `FormFields` renders text/email/password/select/textarea/file, boolean checkbox and string searchable-select fields, built-in BoardOil `emoji`, `style`, `tokenScopes` and `tokenExpiry` fields, and custom Vue components. Emoji fields require `string | null`; style fields require `StyleDraft`; scopes require `string[]` plus allowed scopes; expiry requires `TokenExpiryDraft`. Token controls remain ordinary Vue components, with draft defaults/projection in shared domain helpers. Token name, expiry-range and scope validation belongs to the backend and returns field-keyed errors; the form validates only the UI-only non-expiring acknowledgement. Do not copy backend domain rules into migrated form definitions. Empty finite expiry must remain invalid, because null on the wire means non-expiring. Their component selection belongs to the renderer, while endpoint-specific `errorFields` mappings stay in the form definition. Custom components accept `modelValue` and `disabled` and emit `update:modelValue`. `FormField` renders labels/error associations; compound controls use labelled fieldsets and can map API keys through `errorFields`. Correction clears the field's mapped keys and any declared dependent `clearFields`. `FormFeedback` renders unmapped/general errors inside dialogs; page forms send those errors to a toast and retain field errors beside inputs. Do not add store-action subscriptions or ancestor-form listeners.
- `FormPage` mounts after initial data/choices are loaded. It owns Save, submission feedback, busy navigation blocking and dirty route/beforeunload protection. Once the session has been cleared, navigation to login/unauthorized bypasses the route protection; page-specific data loading, runtime content and success effects remain with the caller. A definition can map successful responses through `savedValues` to adopt canonical values as both the draft and saved baseline. Reset restores the latest baseline; the after-fields slot exposes reset and dirty state for pages that offer it. Configuration uses the existing searchable select, whose input receives field accessibility attributes. Lookup-load failures remain separate from submission errors. Page content slots receive draft values and locked state; `after-fields` supports a live preview without copying draft state into the page.
- Dialog slots supply preview/content and optional footer layout. Confirmed secondary actions share busy/feedback handling, skip save validation, and close on success; cancellation preserves the draft and feedback. Card types use this for delete. Set Default retains its own OK/Cancel dialog and waits for the catalogue refresh before finishing. Cancel while idle discards the draft without an additional prompt.

## Reassessment and Context

- Select fields preserve their declared string/number/null values; select and radio options can derive from the current draft. Fields may opt into `reassessOnChange`. The form's single `reassess` callback receives a draft snapshot and returns values, optional field definitions and an optional lookup error. `useForm` runs it initially, after reset and after flagged edits. It locks edits and submissions while awaiting the result, applies values/fields together without triggering another reassessment, and keeps initial/reset results as the clean baseline. Lookup errors have a separate Retry action and never replace submission validation. Cancel remains available during lookup; disposed forms ignore late assessment results. Controls only render choices and emit user edits. Card transfer keeps board/column loading and permission-dependent policy adjustment in this callback; the board catalogue loader suppresses its banner when the form owns lookup feedback.
- Board-scoped definitions use `isCurrent` to preserve the existing board-ID feedback boundary before submission, after confirmation and on response. Store mutations and busy cleanup retain their own board guards. The existing decision to omit route generations and same-board unmount tracking remains in place. Realtime catalogue updates do not reset an open draft; a different board/entity session creates a new form instance.

## Domain Controls and Existing Forms

- Sign-in and initial-admin setup retain their auth-card layout through the site AuthForm shell, using useForm, FormFields and toast feedback for general errors. They do not use FormPage dirty navigation prompts. Login/setup actions return Results and authStore publishes authenticated state only after matching CSRF acquisition. Setup retains timezone loading/retry before mounting the form and validates only password confirmation locally. If account creation succeeds but session restoration fails, authStore routes to sign-in; its recovery message is consumed there as a toast, while the unmounted setup form ignores the late result. Setup's display name is derived from Username, so backend validation targets the actual input fields.
- Profile and browser-local theme settings use FormPage. Profile loading finishes before the form mounts, with Retry on lookup failure; saves return full Results, adopt canonical display name/email values and update auth/header state through userProfileStore. Avatar cropping, upload and removal remain independent persisted operations and never replace the text draft. Theme uses the ordinary radio field and existing themeStore persistence; changing the draft does not apply a theme until Save. Both pages use the standard dirty navigation protection.
- The user menu applies theme choices immediately through themeStore. The Theme page follows those changes through FormPage's exposed `updateSavedValues` operation: externally saved draft values update the saved baseline and a clean draft, while an unsaved draft is preserved.
- Board-owner and system-administrator Add Member dialogs share one form definition. User choices stay live without resetting the selected user or role; each opening starts a fresh draft. Both membership stores return full Results for additions and leave validation feedback to the dialog. The backend returns user/role field errors, including unavailable users and duplicate membership. Inline role changes and removal retain their independent row operations and feedback.
- Column editing uses FormDialog; inline creation keeps its inline shell with useForm, FormFields and toast feedback for general errors. Board details use FormPage and adopt the canonical saved response; Reset uses that baseline, while package export remains independent of the draft. Board deletion keeps its destructive page shell and typed-name confirmation. Its success continuation navigates after the store disposes the selected board, which unmounts the form. Column and board writes return full Results without duplicate page errors; reordering retains its existing feedback path.
- User and client-account editing share the same ordinary account fields; usernames stay disabled and are omitted from updates. Stores return full Results, update their collections on success, and leave rejection feedback to the form. Password reset uses shared password fields and UI-only confirmation; the backend owns current/new password checks. An incorrect current password returns a field error, not an authentication failure. Self-service reset keeps session clearing in authStore and login navigation in the page after success.
- System Info Message uses auto/presets/solid with the standard palette, shared emoji and style fields, and a page preview. Its form maps prefixed `systemInfoMessage.*` validation keys. The backend owns the conditional title requirement; changing Enabled clears any title error. Saves go through `systemInfoMessageStore.save` to update the app header immediately, and the response becomes the form's clean baseline.
- Style fields can supply `allowedStyleNames` and `presetColours`; omitted settings retain the full style set and standard presets. Slicks use solid/presets with slick preset tokens. Form definitions prepare allowed drafts through the existing style adapters, including fallback for invalid saved values; the shared control owns rendering, not persistence rules. Slick creation loads the board's default style through initial reassessment: the dialog opens immediately, locks editing while loading and permits cancellation. An already-open slick draft stays open if a catalogue refresh removes the slick; do not discard it automatically.
- Tags use shared name/emoji/style fields with backend-owned validation and one complete create request. Name-only quick entry still uses backend-selected colours and existing-tag reuse. Creation loads the default style through initial reassessment, with editing/submission locked and cancellation available. Tag create/update/delete return full Results to the dialog; quick entry retains its own error reporting. Deletion goes through boardStore to clear cached card tag membership.
- Built-in emoji/style fields render reusable ordinary Vue components; the card-type preview remains an ordinary Vue component supplied through a slot. `useStyleDraft` edits the control's existing model reference; style adapters own draft creation and persistence conversion; the forms engine must not own styling rules. Shared token and client-account creation use the same scope/expiry controls. The parent keeps token-list updates and opens the one-time secret dialog from the typed saved result; submission failures belong to the form. Client-account creation returns the complete account/token result, updates the account list in its store and opens the secret dialog in its parent. Other pages and forms await explicit approval.
- Bulk card editing uses selects and a custom adapter around the existing tag tri-state matrix. Its draft keeps slick none/clear/set intent explicit; reassessment shows the slick chooser only for set. The agreed UI-only completeness check requires a chosen slick for set, since null means clear in the backend contract. Selection remains owned by the board view and is cleared only after success; rejected drafts remain open. Bulk-edit store actions return full Results without page errors, while bulkMoveCards preserves the boolean and page-feedback contract used by drag-and-drop.
- Board creation uses reassessment to choose blank/clone/import fields, retaining hidden mode values while submitting only the active operation. `clearFields: 'all'` clears the previous operation's submission feedback on a mode change. Submit labels may derive from the draft. The file control restores the native selection after remount/reset and supports replacement/clearing; file identity participates in dirty checks even when two files share name/size/timestamp. This covers single top-level file fields, not nested uploads or mutable binary editors. Name/description/package validation stays on the backend; clone requires a selected source to address its endpoint. Creation/clone/import store actions return full results and leave submission feedback to the form.
